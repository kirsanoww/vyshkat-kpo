# ВышКат — учёт парка кикшеринга

Домашнее задание №1 по КПО. Python 3.10+, консольный интерфейс, SOLID,
DI-контейнер `dependency-injector`, тесты на `unittest`.

Приложение начинает работу с пустым балансом. Пользователь вводит данные через
меню или передаёт файл с ответами. Демонстрационные объекты не создаются в коде
приложения. Это учитывает корректировку задания об обязательной интерактивности.

## Запуск

Все команды ниже выполняются из папки `vyshkat`, где лежит этот README.

macOS / Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python main.py
```

Windows PowerShell:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

При активированном окружении также работает `python -m vyshkat`.

В меню доступны приём транспорта, добавление вещей, отчёт, подбор транспорта для
новичков и инвентаризация. Для выхода используется `0`. Ошибочный ввод объясняется
сообщением; после этого можно продолжить ввод. `Ctrl+C` или конец ввода завершают
работу. Незавершённый объект на баланс не попадает.

## Демонстрация и ввод из файла

```bash
python main.py --script examples/demo.txt
```

[examples/demo.txt](examples/demo.txt) содержит ответы на те же вопросы меню,
которые задаются при ручном вводе. Файл можно менять или передать свой путь.
Кодировка — UTF-8, допускается BOM; строки, начинающиеся с `#`, — комментарии.
Каждый ответ занимает отдельную строку. При запуске с `--script` ответы печатаются
рядом с вопросами, чтобы демонстрацию было удобно читать.

Сценарий показывает:

- отчёты для пустого парка;
- приём электросамоката, велосипеда и электровелосипеда;
- отказ неисправному транспорту и повторную приёмку после ремонта;
- добавление шлема, механической док-станции и зарядной станции;
- отклонение повторного инвентарного номера;
- обработку неправильной команды, типа, пустого имени, чисел и ответа об исправности;
- все отчёты и завершение работы.

Ожидаемый итог: **5 транспортных средств, 4 вещи, 9 объектов на балансе**.
Энергия транспорта — **5.6 кВт·ч/сутки**, всего баланса — **10.5 кВт·ч/сутки**.
Новичкам подходят `TR-001`, `TR-003`, `TR-004`, `TR-005`.

Коды завершения: `0` — штатный выход, `1` — прерванный ввод объекта,
`2` — ошибка открытия или кодировки файла / аргументов командной строки.
Обработанный отказ техосмотра или исправленная ошибка ввода не означают сбой программы.

## Модель и принятые решения

- [domain.py](vyshkat/domain.py): контракты и неизменяемые объекты.
  `InventoryItem` описывает наименование и инвентарный номер, `EnergyConsumer` —
  суточную электроэнергию. Это структурные интерфейсы `Protocol`:
  соответствие определяется наличием нужных свойств.
- `Asset` содержит общие реквизиты. От него происходят `Vehicle` и `Item`.
  `ElectricScooter` и `ElectricBicycle` наследуют `ElectricVehicle`;
  обычный `Bicycle` не обязан иметь фиктивное поле энергии.
  Вещи представлены `Helmet`, `DockStation`, `ChargingStation`.
- [inspection.py](vyshkat/inspection.py): `ServiceCenter` — контракт техосмотра,
  `BasicServiceCenter` — его реализация. Оператор вводит исправность, сервис
  возвращает решение и причину. Это учебная модель проверки, без датчиков и случайности.
- [fleet.py](vyshkat/fleet.py): `FleetService` принимает транспорт **только после**
  положительного решения техосмотра. Отказ не добавляет объект и не занимает номер.
  Все принятые объекты хранятся в общем словаре; номера уникальны между транспортом
  и вещами. Крайние пробелы убираются; регистр номера имеет значение.
- [cli.py](vyshkat/cli.py): меню, чтение, преобразование ввода и печать.
  Бизнес-логика не вызывает `input()` или `print()` и не знает о консоли или файле.
- [container.py](vyshkat/container.py): сборка зависимостей.
  [__main__.py](vyshkat/__main__.py) выбирает источник ввода и запускает приложение.

Простота — целое число от 1 до 10. Для новичков выбирается только принятый прокатный
транспорт с простотой **не менее 6**; вещи в этот список не входят.
Энергия — конечный неотрицательный `Decimal`, чтобы обычные десятичные значения
суммировались без погрешности двоичного `float`. Ввод принимает точку и запятую.
Отчёт показывает энергию транспорта и энергию всех объектов, включая зарядные станции.
Заданные расходы считаются отдельными величинами; расчёт потерь зарядки не моделируется.

Сотрудники не являются `Asset`: методы приёмки допускают только `Vehicle` и `Item`.
Через добавление вещи нельзя обойти техосмотр транспорта. Объекты после создания
неизменяемы, а списки выдаются как кортежи: вызывающий код не может незаметно поменять
номер принятого транспорта или внутренний баланс.

Хранение — в памяти одного запуска. База данных, сохранение баланса между запусками,
сотрудники и склад пока не реализованы: в задании они обозначены как возможное развитие.
Файл сценария воспроизводит ввод; он не является сохранённой базой.

## SOLID и обязательные вопросы

| Принцип | Как применён |
| --- | --- |
| SRP | Валидация объектов, техосмотр, операции парка, консоль и сборка зависимостей разнесены по модулям. |
| OCP | `FleetService` работает с `Vehicle` и контрактом `EnergyConsumer`, не перечисляет виды транспорта. Новый подкласс участвует в приёмке и отчётах без правки сервиса. |
| LSP | Все виды транспорта сохраняют контракт `Vehicle`: инвентаризация, оценка простоты, исправность. Обычный велосипед не наследуется от электрического и не выбрасывает исключение «энергия не поддерживается». |
| ISP | Инвентаризация и энергопотребление разделены. Шлему и обычному велосипеду не навязывается интерфейс потребителя энергии. |
| DIP | `FleetService` получает абстракцию `ServiceCenter` через конструктор. Реализацию выбирает контейнер, в тестах она заменяется. |

**Наиболее явный принцип — DIP.** В `fleet.py` нет создания `BasicServiceCenter`.
Решение о приёмке поступает от внедрённой зависимости. Тесты с противоположными
решениями сервиса подтверждают, что парк не повторяет проверку самостоятельно.

**Сознательно ограничен OCP на уровне интерфейса.** При добавлении типа нужно дописать
его в `VEHICLE_TYPES` или `ITEM_TYPES` в `cli.py`. Это небольшое изменение точки
регистрации, не переписывание бизнес-логики. Автопоиск плагинов здесь усложнил бы проект.
Отдельный интерфейс хранилища тоже не вводится: пока есть только словарь в памяти,
а отчёты — простые запросы по нему.

**Что изменится при расширении:**

- Новый транспорт наследует `Vehicle` или `ElectricVehicle`, затем регистрируется
  в меню. При прежнем наборе полей сервис парка и отчёты не меняются. Новый особый
  набор полей потребует доработки формы ввода; специальные правила осмотра — сервиса
  техосмотра. Пример расширения проверяет `test_new_transport_type_works_without_changing_fleet_service`.
- Учёт сотрудников потребует самостоятельной модели и сервиса. Наследование от
  `Asset` для сотрудника не нужно; существующий баланс не меняется.
- Штучную запчасть можно моделировать наследником `Item`. Склад с количеством,
  приходом и расходом потребует отдельного складского сервиса: текущая инвентаризация
  учитывает индивидуальные объекты, а не партии товара.

## DI-контейнер и подмена техосмотра

Используется готовый [Dependency Injector](https://python-dependency-injector.ets-labs.org/containers/declarative.html).
`Container` создаёт `BasicServiceCenter` через `Factory`, `FleetService` через
`Singleton`, `ConsoleApp` через `Factory`. Один контейнер хранит один парк;
у разных контейнеров отдельные парки. Контейнер доступен только при сборке приложения
и в тестах, не передаётся в доменную логику как глобальный поиск сервисов.

В [test_container.py](tests/test_container.py) зависимость заменяется **до первого
получения** `container.fleet()`:

```python
center = Mock(spec=ServiceCenter)
center.inspect.return_value = InspectionResult(False, "Запрет тестового сервиса")
container = Container()
with container.service_center.override(providers.Object(center)):
    fleet = container.fleet()
    result = fleet.add_vehicle(vehicle)
```

`vehicle` здесь — объект тестовой фикстуры. Тест
`test_inspection_rejection_can_be_injected_through_container` фиксирует отказ даже
исправному транспорту и проверяет вызов подменённого сервиса. Обратный случай
проверяет `test_fleet_uses_injected_decision_without_repeating_inspection`.
Подмена должна выполняться до создания `Singleton`: уже созданный сервис сохраняет
переданную ему зависимость. Для независимого сценария тесты создают новый контейнер.

В [test_fleet.py](tests/test_fleet.py) тест `test_beginner_threshold_is_six`
проверяет значения 1, 5, 6 и 10; `test_rejected_vehicle_does_not_affect_any_report`
подтверждает, что отклонённый объект не входит в отчёты и список для новичков.

## Проверки

После активации виртуального окружения:

```bash
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
python -m coverage run -m unittest discover -s tests
python -m coverage report -m
python -m ruff check .
python -m ruff format --check .
```

Обычные тесты требуют только runtime-зависимость из `requirements.txt`:
`unittest` входит в Python. `coverage` и `ruff` нужны для покрытия и стиля.
В конфигурации установлен минимальный порог покрытия 60%, учитываются также ветвления.
Проверяются инварианты модели, приёмка и отказ, уникальность номеров, энергия,
правило новичков, расширение модели, подмена через DI и работа меню / файлового ввода.

Результат проверки текущей версии на Python 3.14.3: **46 тестов прошли**,
покрытие с учётом ветвлений — **99%** (все 244 исполняемых оператора покрыты).
Проверки `ruff check` и `ruff format --check` проходят.
